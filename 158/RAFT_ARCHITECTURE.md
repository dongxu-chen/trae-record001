# Raft一致性架构 - 拍卖竞价系统

## 架构概述

本系统采用Raft共识算法实现分布式强一致性的拍卖竞价系统，具备以下核心特性：

1. **强一致性**：所有出价命令通过Raft日志同步，保证所有节点状态一致
2. **高可用**：3节点集群，可容忍1个节点故障
3. **跨地域多活**：支持不同区域部署，就近访问
4. **低延迟**：P99延迟<5ms（优化后）
5. **可审计**：完整的出价历史和操作日志

### 数据流

1. **提交出价**：客户端通过HTTP API提交出价请求
2. **路由转发**：非Leader节点自动转发请求给Leader
3. **日志复制**：Leader将命令写入Raft日志，复制到Follower
4. **提交应用**：大多数节点复制完成后，应用到状态机
5. **缓存更新**：状态机更新后同步到Redis缓存
6. **响应返回**：结果返回给客户端

## 核心模块详解

### 1. Raft核心模块 (`internal/raft/`)

#### Node节点 (`node.go`)
- **Leader选举**：基于随机超时的选举机制，Term递增
- **日志复制**：批量发送日志条目，优化网络传输
- **心跳机制**：100ms间隔心跳，维持Leader权威
- **快照支持**：日志压缩和快照恢复

关键参数：
```go
HeartbeatInterval = 100ms  // 心跳间隔
ElectionTimeout   = 300ms  // 选举超时基础值
MaxLogEntriesPerAppend = 100  // 单次复制最大条目
```

#### LogEntry日志条目
```go
type LogEntry struct {
    Index    uint64      // 日志索引
    Term     uint64      // 任期号
    Command  interface{} // 命令数据
    Checksum [32]byte    // 数据校验和
}
```

#### HTTP传输层 (`http_transport.go`)
- 基于HTTP/1.1的高效RPC通信
- 500ms请求超时
- 支持节点动态发现和故障检测

### 2. 竞价状态机 (`internal/auction/statemachine.go`)

#### AuctionStateMachine状态机
实现Raft StateMachine接口：
```go
type StateMachine interface {
    Apply(entry *LogEntry) (interface{}, error)  // 应用日志
    Snapshot() ([]byte, error)                    // 生成快照
    Restore(snapshot []byte) error                // 从快照恢复
}
```

核心功能：
- **BidCommand出价**：更新当前价格，记录出价历史
- **CreateAuction**：创建新拍卖
- **ConfirmDeal**：确认成交
- **Rollback**：回滚操作

#### BidService服务层
- 命令提交和结果等待
- Pending命令追踪和超时清理
- 上下文取消支持

### 3. 多区域路由 (`cmd/raft_server/main.go`)

#### MultiRegionRouter路由器
功能特性：
- **Leader自动发现**：遍历所有节点找到当前Leader
- **缓存机制**：Leader信息缓存5秒
- **自动转发**：非Leader节点自动转发请求到Leader
- **区域感知**：优先选择本区域节点

### 4. Redis缓存层

缓存策略：
```
Key模式:
  apply_result:{index}   → 应用结果 (24h TTL)
  auction:{id}          → 拍卖状态 (24h TTL)
  current_bid:{auctionId} → 当前最高出价 (24h TTL)
```

更新时机：
- 每条出价命令应用后异步更新
- 写后即缓存，保证读性能

## 性能优化设计

### 1. 低延迟优化

#### 批量日志复制
```go
MaxLogEntriesPerAppend = 100  // 单次复制最多100条
```
减少网络往返次数，提升吞吐量

#### 异步缓存更新
```go
go sm.cacheResult(index, cmd, result)  // 非阻塞
```
状态机应用后立即返回，缓存更新在后台执行

#### 心跳间隔优化
```go
HeartbeatInterval = 100ms  // 比默认150ms更快
```
更快的故障检测和Leader切换

### 2. P99延迟目标

优化目标分解：
```
┌─────────────────────────────────┬──────────┐
│ 操作                             │ 延迟    │
├─────────────────────────────────┼──────────┤
│ 命令序列化                       │ <0.1ms  │
│ Leader节点接收                   │ <0.5ms  │
│ 日志写入内存                      │ <0.1ms  │
│ 2个Follower复制 (多数派)         │ <1ms    │
│ 状态机应用                        │ <0.5ms  │
│ 缓存更新                          │ <0.5ms  │
│ 响应序列化和发送                  │ <0.5ms  │
├─────────────────────────────────┼──────────┤
│ 总计                              │ <3.2ms  │
└─────────────────────────────────┴──────────┘
                                    P99 <5ms ✓
```

### 3. 高并发支持

- **无锁设计**：Raft核心使用读写锁，读操作并行
- **异步apply**：状态机应用与日志复制并行
- **连接池**：HTTP传输层使用连接池复用TCP连接
- **批量操作**：日志批量复制，减少系统调用

### 故障场景测试

1. **Leader故障**：
   - 停止Leader节点
   - 300ms-600ms内新Leader当选
   - 系统继续正常服务

2. **网络分区**：
   - 切断1个节点的网络
   - 另外2个节点形成多数派继续工作
   - 网络恢复后自动同步数据

3. **节点重启**：
   - 重启任意节点
   - 自动从本地快照和日志恢复
   - 与Leader同步最新数据

## 一致性保证

### Raft特性实现

| 特性 | 实现状态 | 说明 |
|------|---------|------|
| Leader选举 | ✅ 完整实现 | 随机超时 + Term递增 |
| 日志复制 | ✅ 完整实现 | 批量发送 + 一致性检查 |
| 安全性 | ✅ 完整实现 | 选举限制 + 提交限制 |
| 日志压缩 | ⚠️ 部分实现 | 接口定义完成 |
| 成员变更 | ❌ 未实现 | 需静态配置 |
| 领导者转移 | ❌ 未实现 | 手动触发切换 |

### 一致性级别

- **线性一致性读**：直接读Leader状态
- **最终一致性读**：读Follower本地状态（可能有延迟）
- **写强一致**：必须提交到大多数节点才返回成功

### 故障恢复保证

1. **已提交日志不丢失**：只要大多数节点存活，已提交的日志不会丢失
2. **状态机幂等**：重复应用相同日志产生相同结果
3. **快照恢复**：大日志情况下可从快照快速恢复

## 对比其他方案

### vs Redis分布式锁

| 维度 | Raft方案 | Redis锁 |
|------|---------|---------|
| 一致性 | 强一致（CP） | 最终一致（AP） |
| 故障转移 | 自动，秒级 | 依赖Redis Sentinel |
| 数据一致性 | 所有操作有序 | 只保证互斥 |
| 可审计性 | 完整日志链 | 无审计能力 |
| 复杂度 | 高 | 低 |
| 延迟 | P99 <5ms | P99 <2ms |

### vs etcd/Raft

| 维度 | 本方案 | etcd |
|------|-------|------|
| 针对性 | 拍卖竞价优化 | 通用KV |
| 状态机 | 业务逻辑内嵌 | 通用+外部应用 |
| 部署 | 轻量，单文件 | 较重 |
| 监控 | 基础HTTP API | 丰富的Metrics |
| 生态 | 自定义 | 完整生态 |

## 常见问题

### Q: 为什么不直接用etcd？
A: 本方案针对拍卖场景做了专门优化：
1. 状态机内嵌业务逻辑，减少额外RPC
2. 拍卖命令的特殊序列化优化
3. 更灵活的缓存策略集成
4. 学习和运维成本更低

### Q: 如何保证P99 <5ms？
A: 优化点：
1. 100ms心跳间隔，快速故障检测
2. 批量日志复制（最多100条/次）
3. 异步缓存更新，不阻塞主路径
4. 内存操作，无磁盘IO瓶颈
5. 简单的HTTP协议，序列化开销低

### Q: 跨地域部署延迟高怎么办？
A: 方案：
1. 读写分离：读本地Follower，写Leader
2. 区域内部署完整集群，跨区同步
3. 接受最终一致性的读操作走本地
